# TZ 018 — NanoID UID identity model: decouple unique IDs from human slugs

Audience: Flash coder / literal executor.

Goal: stop using title-derived slugs as primary identifiers. Introduce short NanoID-based UIDs as canonical IDs, while keeping slugs as human-readable labels for feature/wave/packet naming, search, and UI display.

This fixes the golden problem where creating the same titled feature twice returns the old failed feature because `feature_id = FEAT-{slug}` is deterministic.

---

## 0. Design decision

Use two separate concepts everywhere:

```text
uid  = opaque unique identifier, generated by NanoID, used for DB PK/API identity/links
slug = human-readable stable-ish label derived from title, not globally unique
```

Do **not** concatenate NanoID into the slug.

Bad:

```text
feature_id = FEAT-golden-smoke-live-002-K7F3P9QX
```

Good:

```text
feature.uid  = feat_K7F3P9QX
feature.slug = golden-smoke-live-002
feature.title = Golden Smoke Live 002
```

Same for waves and packets:

```text
wave.uid   = wave_Q8LM2ZAP
wave.slug  = sandbox-normal

packet.uid  = pkt_T4V9K2MA
packet.slug = add-date-util
```

The UI may show both:

```text
Golden Smoke Live 002 · feat_K7F3P9QX
W01 Sandbox normal · wave_Q8LM2ZAP
P01 Add date util · pkt_T4V9K2MA
```

But APIs and DB relations must use `uid`.

---

## 1. Current problem in code

Current `architect.py` does deterministic ID generation from title slug:

```python
slug = _slugify(title)
feature_id = f"FEAT-{slug.upper()}"
```

Then it returns an existing feature if the same feature ID already exists:

```python
existing_feature = db.query(Feature).filter_by(id=feature_id).first()
if existing_feature:
    return existing feature
```

This breaks repeat golden runs:

```text
same title → same slug → same feature_id → old failed feature reused
```

Current wave/packet IDs are also deterministic and derived from title/order:

```python
wave_id = f"{slug.upper()}-W{i:02d}"
packet_id = f"{feature_id}-{wave_id}-P{j:02d}-{action}"
```

This makes retries, repeated golden runs, and duplicated feature titles collide.

Relevant current schema:

```text
Feature.id primary key
Feature.slug
Wave.id primary key
Wave.feature_id
Wave.slug
Packet.id primary key
Packet.feature_id
Packet.wave_id
Packet.slug
```

---

## 2. Chosen migration strategy

Keep the existing DB column name `id` for now to avoid a giant migration.

But change its meaning:

```text
Feature.id = generated feature UID
Wave.id    = generated wave UID
Packet.id  = generated packet UID
```

Keep existing `slug` fields as human-readable slugs.

Do **not** add a new global top-level ID above feature/wave/packet yet. It creates extra complexity without solving the collision problem. Feature/Wave/Packet already need their own canonical identity.

Optional future rename:

```text
id → uid
```

but do not do that rename in this task unless trivial. For now, treat `id` as UID and document it.

---

## 3. UID format

Implement a small internal NanoID helper. Do not add a heavy dependency if avoidable.

Suggested file:

```text
src/grace_control/core/uid.py
```

Implementation:

```python
import secrets
import string

_ALPHABET = "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz"

def nanoid(size: int = 10) -> str:
    return "".join(secrets.choice(_ALPHABET) for _ in range(size))

def new_feature_uid() -> str:
    return f"feat_{nanoid(10)}"

def new_wave_uid() -> str:
    return f"wave_{nanoid(10)}"

def new_packet_uid() -> str:
    return f"pkt_{nanoid(10)}"

def new_run_uid() -> str:
    return f"run_{nanoid(10)}"
```

Use lowercase prefixes:

```text
feat_
wave_
pkt_
run_
```

10 chars is enough for internal control-plane IDs and still readable.

Examples:

```text
feat_K7F3P9Qx2L
wave_A9mP2qR7Vz
pkt_T4V9K2mA1b
run_E3nQ8zL0Xp
```

## 4. Collision handling

NanoID collisions are unlikely, but code must still be deterministic on collision.

Add helper:

```python
def generate_unique_id(db, model, factory, *, max_attempts: int = 5) -> str:
    for _ in range(max_attempts):
        value = factory()
        if db.query(model).filter_by(id=value).first() is None:
            return value
    raise RuntimeError("failed to generate unique id")
```

Use it for `Feature`, `Wave`, `Packet`, and any future run ID that is DB primary key.

## 5. Architect plan creation behavior

File:

```text
src/grace_control/api/routers/architect.py
```

### 5.1 Feature ID generation

Replace:

```python
feature_id = f"FEAT-{slug.upper()}"
```

with:

```python
feature_id = generate_unique_id(db, Feature, new_feature_uid)
```

But note: current code computes `feature_id` before opening DB because context warming uses it.

Required approach:

1. Compute slug immediately:

```python
slug = _slugify(title)
```

2. Generate a temporary trace/display ID for logging before DB if needed, or open DB earlier.

Simplest acceptable approach:

```python
with get_db() as db:
    feature_id = generate_unique_id(db, Feature, new_feature_uid)
```

Then use that feature_id for context logs and DB persist.

If context warming needs `feature_id` before DB block, generate UID before context using `new_feature_uid()`, then when persisting check collision and regenerate only if needed. Keep this small.

### 5.2 No more automatic idempotency by title

Remove this behavior:

```python
existing_feature = db.query(Feature).filter_by(id=feature_id).first()
if existing_feature:
    return existing feature
```

Because `feature_id` is now random and unique.

If caller wants idempotency later, add explicit `idempotency_key` in a separate future task.

For this task:

```text
POST /api/architect/plan creates a new feature every time unless explicit feature_id is provided.
```

### 5.3 Optional explicit feature_id for tests/imports

Support optional explicit ID only for internal/test use:

```python
explicit_feature_id = spec.get("id") or spec.get("feature_id")
```

Rules:

```text
if explicit ID is provided:
  validate it starts with feat_ or FEAT-legacy for backward compatibility
  if already exists, return 409 or existing only if request has allow_existing=true
if no explicit ID:
  generate new feat_ UID
```

For minimal patch, you may skip explicit ID support, but do not keep title-based ID reuse.

```text

```

## 7. Packet ID generation

Replace deterministic packet IDs:

```python
packet_id = f"{feature_id}-{wave_id}-P{j:02d}-{action}"
```

with:

```python
packet_id = generate_unique_id(db, Packet, new_packet_uid)
```

Keep:

```python
packet.slug = _slugify(pkt_spec["title"])
packet.spec_json["action"] = action
packet.spec_json["display_order"] = j
```

If packet display needs P01, compute from order within wave. If there is no packet order column, store it in `spec_json["display_order"]` for now.

Do not rely on packet ID for order, title, action, or wave relation.

## 8. Dependency resolution must stop depending on generated packet IDs from deterministic action strings

Current DAG building uses:

```python
action = _extract_action(pkt_spec["title"])
pid = f"{feature_id}-{wave_id}-P{j:02d}-{action}"
action_to_id[action] = pid
```

With random IDs, this must still work.

Required approach:

Before DAG validation/persist, assign generated packet UIDs in memory.

Build an in-memory plan index:

```python
planned_packets = []
action_to_packet_id = {}
```

For each packet:

```python
packet_id = new/generated pkt UID
action = _extract_action(pkt_spec["title"])
action_to_packet_id[action] = packet_id
planned_packets.append({...})
```

Then resolve dependencies:

```python
resolved_depends_on = [action_to_packet_id.get(dep, dep) for dep in depends_on]
```

DAG validator should receive UID packet IDs.

Persist the same generated packet IDs later.

Important: do not generate packet IDs twice. Generate once, store in memory, reuse for DAG and DB persist.

## 11. Golden scripts / run scripts

Update golden scripts so they no longer depend on deterministic feature IDs.

Bad:

```text
DELETE /api/features/FEAT-GOLDEN-SMOKE-LIVE-002
expect feature_id == FEAT-GOLDEN-SMOKE-LIVE-002
```

Good:

```text
POST /api/architect/plan
read response.data.feature_id
use returned feature_id for polling/reporting
```

If the same title is posted twice, expect two different feature IDs:

```text
feat_A...
feat_B...
```

Run ID can still be used for state/report directory names, but not as DB primary key unless explicitly requested.

## 13. Worktree/branch naming

Worktree/branch names currently often include packet_id. New packet IDs are short, so this is good.

Expected branch examples:

```text
agent/default/pkt_T4V9K2mA1b/attempt-0001
```

This is better than giant title-derived branch names.

Make sure no code assumes packet IDs contain feature/wave/action parts.

Search for string splits or assumptions:

```text
.split("-W")
.split("-P")
startswith("FEAT-")
contains "P01"
contains "W01"
```

Remove or replace those assumptions.

## 14. Backward compatibility / migration

Because this is still pre-production, a full DB migration is not required unless tests require it.

But code must tolerate old rows during transition:

```text
old feature id: FEAT-GOLDEN-SMOKE-LIVE-001
new feature id: feat_K7F3P9Qx2L
```

Do not crash when reading old IDs.

However, new plans must always generate new UID IDs.

Admin UI should display old IDs as UID field too, but optionally mark them legacy if they start with `FEAT-`.

## 16. Acceptance criteria

Done only if:

1. New feature creation with the same title twice creates two different Feature.id values.
2. Feature.slug remains the same readable slug for both.
3. Wave.id and Packet.id are generated UIDs, not title-derived deterministic strings.
4. Dependencies still resolve correctly.
5. API responses return UID IDs and slugs separately.
6. Admin UI shows UID and slug/title separately.
7. Golden scripts use returned feature_id, not deterministic title-derived ID.
8. No new code assumes IDs contain slug/order/action.
9. Old legacy IDs can still be read without crashing.
10. Existing FAST golden still passes.
